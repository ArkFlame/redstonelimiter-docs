THE MECHANICS

How limiting works

RedstoneLimiter watches circuit activity in four nested areas. Understanding the size of each area is the key to sensible limits. The short animations below show exactly how the settings work.

The four scopes #

ScopeActual sizeWhat it answersDefault base max
BlockOne exact x/y/z positionIs this particular device firing too often?Per material (e.g. piston 3)
Subchunk16 × 16 × 16 blocksIs a compact part of the machine too busy?96
Chunk16 × 16 block footprint, full heightIs the total redstone activity in this chunk too high?1024
Region32 × 32 chunks, full heightIs a very large area collectively too active?96
Potential surprise: A single region covers 1,024 chunks horizontally. Its default base max of 96 is shared across the region, not 96 per chunk. If only a local machine should be controlled, consider your region settings carefully. A region is not a Folia execution region.

Each event is counted at the reached scope. The engine checks block → subchunk → chunk → region, and returns as soon as a scope blocks. A blocked block activation therefore does not also advance that attempt through all broader counters.

What does a period mean? #

config.yml
period:
  duration-millis: 5000  # Count activity over 5 seconds
  sustain-millis: 2000   # Temporarily block for at least 2 seconds
  sliding: true         # Rolling window, not a fixed reset

With a configured max of 5 and no multiplier: activations 1–5 are allowed. Activation 6 is blocked. Further over-limit attempts are still counted at that scope and can extend its temporary blocked-until time.

SLIDING: TRUE

Rolling window

Look at the recent duration (using bounded time buckets). Old activity gradually falls out of the count.

SLIDING: FALSE

Fixed window

Use a period that resets when its configured duration has elapsed. Existing sustain can continue beyond the reset.

The duration controls counting. Sustain controls temporary blocking. Neither setting permanently quarantines chunks.

Which game events are observed? #

  • Redstone current transitions: event counts when the current actually changes. A blocked transition restores the old current.
  • Observers: activity observed through block-physics events, with a configurable deduplication period. Those physics events cannot themselves be cancelled by the listener.
  • Dispensers and droppers: monitored through dispense events.
  • Pistons: extend and retract events are monitored. Maximum push length is checked separately by max_piston_push.

How do preset and TPS influence the max? #

Effective threshold (source formula)
effectiveMax = ceil(baseMax × presetMultiplier × tpsMultiplier)

baseMax = 0 → unlimited for that scope / material

STRICT = 1×, BALANCED = 1.5×, LENIENT = 2×. With default TPS scaling, ≤16.0 TPS uses 1×, ≥19.5 uses 2×, and TPS in between interpolates. These multipliers alter the maximum count, not the time window or sustain.

What about whitelists and quarantine? #

  • Whitelisted chunks: record telemetry but do not automatically threshold-block. The independent piston push-size rule can still cancel an extension.
  • Manually quarantined chunks: block monitored cancellable circuit activity across the chunk, overriding whitelist entries. Observer physics events cannot themselves be cancelled. They remain quarantined until an administrator changes the policy.
  • Disabled worlds: skip counting, blocking, visual effects and notifications completely.

None of these are automatically added to manual quarantine when a temporary activity limit is exceeded.
