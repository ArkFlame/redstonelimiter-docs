EXAMPLE 01 / RECOMMENDED STARTING POINT

Stop a compact lag machine without limiting a huge region

Use the precise block and subchunk limits, while leaving the larger aggregates off. This is a suggested starting example, not the source default and not a guaranteed best value for every network.

config.yml — edited sections
anti-lag:
  preset: "STRICT"

blocks:
  enabled: true
  period:
    duration-millis: 5000
    sustain-millis: 2000
    sliding: true
  max-activations:
    DEFAULT: 5
    PISTON: 3
    STICKY_PISTON: 3
    OBSERVER: 8

subchunks:
  enabled: true
  period:
    duration-millis: 5000
    sustain-millis: 2000
    sliding: true
  max-activations: 96

chunks:
  enabled: false
  period:
    duration-millis: 5000
    sustain-millis: 2000
    sliding: true
  max-activations: 1024

regions:
  enabled: false
  period:
    duration-millis: 5000
    sustain-millis: 2000
    sliding: true
  max-activations: 96

The blocks.max-activations section shown is a partial material override. Keep the other material entries from your existing file unless you deliberately want their built-in/default behavior. Turning off chunks and regions does not turn off counting; those scopes still record telemetry.

EXAMPLE 02 / PROTECT NORMAL FARMS

Allow more piston activity while keeping protection

Sometimes a farm gets limited because one piston cycles often. Increase that individual material's base maximum. Other scopes must still have room, or they may block the same machine.

config.yml
# Change these existing keys under blocks.max-activations:
blocks:
  max-activations:
    PISTON: 12
    STICKY_PISTON: 12

With STRICT and healthy TPS scaling enabled, a base limit of 12 becomes an effective 24. At degraded TPS it remains 12. Use the calculator to explore.

EXAMPLE 03 / REGION-WIDE LAG

Protect a whole region from aggregate activity

When multiple chunks collectively produce too much activity, region limiting can help. Start higher than a very restrictive region-wide threshold if you don't want neighboring farms affected.

config.yml
regions:
  enabled: true
  period:
    duration-millis: 5000
    sustain-millis: 2000
    sliding: true
  max-activations: 1024

This example value is intentionally not the shipped default: the source default is 96, and a region encompasses 1,024 chunks. Check your own load profile first; a higher max is more permissive.

EXAMPLE 04 / EXCEPTIONS

Whitelist a safe machine or exclude a whole world

config.yml
whitelist:
  chunks:
    - "world/3/-2"     # Chunk X=3, Z=-2 in world

disabled-worlds:
  - "creative"         # Entire creative world is not monitored

Use actual Bukkit world names and chunk coordinates. A whitelisted chunk still has activity recorded, but automatic limits do not block there. A disabled world skips all counting, blocking, effects and notifications.

EXAMPLE 05 / EMERGENCY ACTION

Manually quarantine one chunk

config.yml
quarantine:
  manual-chunks:
    - "world/3/-2"

This is a deliberate administrative restriction: it stays until removed. It overrides a whitelist entry for the same chunk. For temporary automatic restrictions, tune max-activations, duration-millis, and sustain-millis instead.

EXAMPLE 06 / PREDICTABLE MAXIMA

Use fixed effective maxima regardless of TPS

config.yml
anti-lag:
  preset: "STRICT"
  tps-scaling:
    enabled: false
    degraded-tps: 16.0
    healthy-tps: 19.5
    min-multiplier: 1.0
    max-multiplier: 2.0

With STRICT and TPS scaling disabled, effective max is simply the base max. You are disabling automatic TPS responsiveness, not the limiter itself.
